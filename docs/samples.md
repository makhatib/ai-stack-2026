# The demos, and how to check them

<!-- AISTACK-LOCAL-MODE:BEGIN -->
Not published to the internet. Reachable on this machine; reachable from other devices on your network if your network allows it — we have not tested that.
<!-- AISTACK-LOCAL-MODE:END -->

This stack ships **four n8n templates, three of which run**:

| | Demo | What it claims | |
|---|---|---|---|
| **W1** | Research over a local corpus | a question is embedded, the nearest chunks are fetched from pgvector, and the model answers from those chunks and cites them | runs |
| **W2** | Chat with your PDF | a PDF is parsed by Docling, embedded through LiteLLM, and stored next to the corpus | **deferred** |
| **W3** | Scheduled summary behind the approval envelope | a daily summary is written, a human decides it, and only then is it dispatched — once | runs |
| **W4** | Webhook to model to stored result | a POST with a header token is answered by the local model and the result is stored | runs |

W2 is **deferred by decision**, not broken and not pending anybody: n8n has no
route to Docling, and this release will not add one to make a demo pass. The
measurement and the decision are in [section 3](#3-w2-is-deferred-and-this-is-why).
Its template is still imported and still bound, so it is ready the day that
route is bought by a product requirement.

**An import is not a demo.** `aistack samples load` imports the templates and
exits 0; for most of 2026-10-18 that was all anyone had checked, and not one
of the four could actually run — no model weights, no credentials attached to
any node, no tables for the SQL to write to, no question for W1 to ask and no
human decision anywhere in W3. The commands below are the difference, and
every one of them checks its own output.

Everything here is synthetic. No real credential, no real document, and
nothing in this release sends a message to anybody: W3 "delivers" by writing a
row to a table.

---

## 1. Set it up

```sh
bin/aistack up            # if the stack is not already running
bin/aistack samples setup
```

`samples setup` is idempotent — run it twice and nothing doubles. It:

1. **pulls the two models the templates call** (`local-embed` and `local-chat` in
   `config/litellm/config.yaml`: `nomic-embed-text` and `qwen3.5:2b`) through
   the model-puller helper, then re-reads `ollama list` and refuses to continue
   if either is still missing;
2. **creates the `aistack_demo` database** and a role of the same name, applies
   the approval envelope from `config/postgres/init/02-approval-envelope.sql`
   (the shipped file, not a copy of it) and the demo tables from
   `samples/fixtures/schema.sql`;
3. **mints three demo credentials** — a Postgres login, a LiteLLM *virtual* key
   with its own small budget, and a random 48-hex-character token for W4's
   webhook — writes them `0600` under `secrets/` and imports them into n8n with
   fixed ids, which is what lets the templates bind to them by id. It also
   re-imports the backup drill's two **ballast** credentials
   (`samples/credentials.synthetic.json`, ids `aistackDrillSyn1` and
   `aistackDrillSyn2`) and asserts there are exactly two of them, not two more
   per run;
4. **imports all four workflows** with fixed ids, asserts all four are inactive,
   and asserts a re-import leaves four rather than eight. Four are imported and
   bound, including the deferred W2; three are executable;
5. **embeds the corpus** in `samples/corpus/` and generates
   `samples/fixtures/synthetic.pdf` from `make-synthetic-pdf.py`.

The three generated secrets are `secrets/samples_demo_db_password`,
`secrets/samples_demo_litellm_key` and `secrets/samples_demo_w4_token`. Nothing
prints their values — `samples setup` prints the paths.

## 2. Run the demos

```sh
bin/aistack samples run all      # or: run W1 / W2 / W3 / W4 / P2
```

**It is slow, and the slowness is the stack.** Every answer is generated by a
3B model on CPU. On an otherwise idle four-core box a full `run all` takes
around eight minutes; on a loaded one it takes several times that. Two ceilings
bound it: each model call has an 840-second timeout, and no n8n execution may
exceed `EXECUTIONS_TIMEOUT_MAX` (900s, from `limits.yaml`). That is why the
demo templates ask for at most 160 tokens — enough to show a cited answer,
small enough to finish on a machine that is also doing something else.

Each case prints `PASS`, `FAIL`, `DEFERRED` or `BLOCKED` with the evidence
underneath it. Exit codes, so this can be the last line of a release check:

| code | meaning |
|---|---|
| 0 | nothing failed. Every executable case passed; a **deferred** case may be reported and counted — see W2 below |
| 1 | at least one case **failed** |
| 2 | nothing failed, but at least one case is **blocked** |

**`DEFERRED` and `BLOCKED` are different states and the difference is the
point.** Blocked means an *open* question: the demo cannot reach something and
nobody has decided what to do about it. Deferred means somebody with the
authority to decide looked at it and said no. A release check that goes red for
a recorded decision is a release check people start passing with `|| true`, so a
deferral exits 0 — while still printing, counting and naming itself on every
run. Nothing in this release is blocked; `run all` exits 0 with one deferral.

Every assertion reads the database rather than the n8n CLI's output, which has
two consequences worth knowing: a run a person did by hand in the n8n editor is
graded by exactly the same checks, and the evidence for a failure is still in
the tables afterwards.

### What gets checked

**W1 — research over a local corpus.** The workflow asks a fixed synthetic
question, and the harness asserts that the nearest chunk came from the file
`samples/fixtures/schema.sql` names in `w1_expected` (`02-retrieval.md`), that
the distances really are ascending — so the `ORDER BY` ran, rather than row
order being luck — and that a non-empty answer was recorded in `w1_runs`
alongside the sources it cited.

**W4 — webhook to model to stored result.** Six requests, one of which is
supposed to work. The harness accepts either `401` or `403` for a rejected
credential — which one you get is n8n's choice, not the template's — and this
stack answers `403`:

| request | expected | measured |
|---|---|---|
| right token | the model's answer stored in `w4_results` | `200` |
| no token | nothing stored | `403` |
| wrong token | nothing stored | `403` |
| right header name, empty value | nothing stored | `403` |
| the right token in the **wrong header** | nothing stored | `403` |
| right token, no `prompt` in the body | refused, nothing stored, no inference paid for | `500` |

W4's webhook has to be *registered* by a running n8n before any of that can be
tested, and n8n registers webhooks only when a main process starts —
`publish:workflow` says so itself: *"changes will not take effect if n8n is
running"*. So `samples run W4` publishes the demo, starts a **throwaway n8n
container** on the same internal bridges to serve it, runs the cases against
that, stops it and unpublishes. The long-running instance is never restarted
and never reconfigured.

**While the demo is published, it answers on every running n8n, including the
one behind the reverse proxy.** MEASURED (NOM-302): registration lives in
`webhook_entity` in Postgres, not in one process's memory, so the throwaway
container's registration makes the route live everywhere. The harness asserts
that (W4.6) rather than the comfortable opposite, which is what it was written
to assert before the measurement corrected it.

What keeps the demo off the proxy today is **not** this harness's choice of
container. It is that Caddy forwards `/n8n/webhook/*` without stripping the
prefix, so n8n has no route for what arrives — a bug standing in for a control
(measured and routed on [NOM-321](/NOM/issues/NOM-321)). W4.8 therefore asserts
the property that does matter: once the demo is unpublished, the live instance
answers `404` again.

**P2 — the approval envelope, on its own.** Five negative cases and one
positive one, run directly against the shipped DDL rather than against a copy:

| case | what it proves |
|---|---|
| P2.1 | an illegal state transition (`pending -> executed`) is refused by the trigger, not merely absent from a `CHECK` |
| P2.2 | the recipient and the parameter hash of an existing envelope cannot be rewritten |
| P2.3 | every transition is logged, and the log cannot be `UPDATE`d or `DELETE`d |
| P2.4 | one approval cannot be claimed twice — the second claim affects zero rows |
| P2.5 | an expired approval cannot be claimed at all |
| P2.6 | changing the summary **after** approval makes the dispatch refuse and marks the envelope `failed`/`refused` |

**W3 — the one that needs a person.** W3 is a state machine and the harness
grades whichever state it is in:

```sh
bin/aistack samples run W3          # nothing approved -> writes ONE request and stops
bin/aistack samples approve <id>    # the human decision (add --reject to refuse)
bin/aistack samples run W3          # now dispatches, once, and proves it
```

- With nothing approved, the run writes a pending envelope whose SHA-256 covers
  exactly the summary text that was frozen, delivers nothing, and prints the
  `approve` command with the action id.
- Run it again before deciding and it writes **no second request**. One
  approval per day, not one per run; stacking identical approvals in front of a
  human is how approval fatigue gets engineered in.
- `samples approve` prints the envelope — state, named approver, recipient,
  scope, parameter hash, expiry — and then asks. It **refuses to act for any
  subject other than the one the envelope names**, refuses anything that is not
  `pending`, and refuses an expired envelope. In the deployed stack that
  subject comes from Authelia's `Remote-User` header, which the proxy sets and
  no workflow can supply.
- After approval, the next run claims the envelope atomically, recomputes the
  hash over the text it is about to deliver, writes one row to `w3_delivered`,
  and marks the envelope `executed`/`ok`. The harness then checks that what was
  delivered is byte-identical to what was approved, that the transition log
  reads `pending -> approved -> executing -> executed`, and that a replayed
  claim affects zero rows.
- Run it once more and it does nothing at all: today's summary has already gone.

## 3. W2 is DEFERRED, and this is why

`samples run W2` reports `DEFERRED` — not `PASS`, not `FAIL`, and not
`BLOCKED`. The template is complete: its document is generated, its embed and
store nodes are bound, and its SQL is parameterised. Its parse step cannot
complete in this release, because n8n has no route to Docling:

```
$ docker exec aistack-n8n wget -T5 -O- http://docling-serve:5001/health
wget: bad address 'docling-serve:5001'
```

The harness measures the same thing with its own in-container HTTP probe, and
it fires that probe **twice** — once at Docling, once at LiteLLM, which n8n is
supposed to reach:

```
litellm:4000/health/liveliness  -> status 200, "I'm alive!"
docling-serve:5001/health       -> status 0,   ERROR getaddrinfo EAI_AGAIN docling-serve
```

The second line is only a measurement because the first one succeeded. If the
control probe fails, `W2.3` reports `FAIL` and says no conclusion about Docling
can be drawn from that run — a probe that cannot report success is not evidence
of anything. (The first version of this gate ran `getent`, which is not in the
n8n image at all: empty output, the same answer whatever the topology. Review
caught it.)

Docling sits on a pairwise /29 whose only other member is Open WebUI; n8n is on
`apps`, `gateway` and `data`. There is no route between them, by design:
Docling is the component most likely to be processing a file an attacker wrote,
and n8n is the component holding every credential in the stack.

### The decision

This is settled, not waiting on anyone. **No new Docling peer is added to make
a demo pass** ([NOM-321](/NOM/issues/NOM-321)):

- `parse-n8n` — a bridge from the automation engine to the parser — is
  **rejected**. `docling-serve` is `confined` on a `pairwise` /29, so a third
  member fails invariant I1 outright, and this release's own precedent (the
  reserved `parse-agw`) says a new consumer of Docling gets its own pairwise
  bridge rather than a seat on an existing one.
- The indirect route — n8n → Open WebUI `/api/v1/files` → Docling — is
  **rejected too**. It needs `Remote-Email` self-injection or an API key this
  offline harness cannot mint, so it is not a workaround.
- A parser peer returns only through the reserved `parse-agw` bridge, with a
  passed G-AGENTS or its own named gate — bought by a product requirement, not
  by a demo's completeness.
- W2 therefore defers with the `agents` group, like W6, and
  [NOM-323](/NOM/issues/NOM-323) fixes the shipped profile at three executable
  n8n demos: W1, W3 and W4.

The template is still written so that it starts working the day such a bridge
exists: the probe above detects the route and the harness grades W2 like W1 the
moment it is there. If that branch ever fires, read NOM-321 first — the route
appearing is either a product decision or a mistake, and the harness says so.

## 4. Take it away

```sh
bin/aistack samples teardown
```

This removes the four demo workflows and three demo credentials from n8n, drops
the `aistack_demo` database and role, **revokes** the LiteLLM virtual key
rather than merely forgetting it, and deletes the three generated secrets and
the generated PDF.

**One thing setup creates survives teardown on purpose:** the two ballast
credentials in `samples/credentials.synthetic.json`. They are `samples load`
state, not demo state — `aistack drill run` exports and decrypts them to prove
the n8n encryption key travelled with the archive, and with zero credentials in
the database that assertion degrades to a printed note rather than a failure
(`scripts/drill.sh`). Their ids are deliberately outside the `aistackDemo%`
pattern teardown deletes by. They are bound to nothing and hold only
`SYNTHETIC-NOT-A-REAL-…` values. Remove them deliberately if you want a clean
n8n:

```sh
docker exec aistack-postgres psql -U aistack_admin -d n8n \
  -c "DELETE FROM credentials_entity WHERE id IN ('aistackDrillSyn1','aistackDrillSyn2')"
```

Doing that leaves the next `aistack drill run` with no ciphertext to decrypt
until something imports a credential again.

It deliberately does **not** delete the model weights: they are shared with the
rest of the stack, and a teardown that silently removed a 2 GB download would
be a teardown nobody runs twice. Remove them on purpose instead, with the stack
down:

```sh
bin/aistack down
docker volume rm aistack-ollama-models
```

**To roll back the change itself** rather than the demo data: `samples setup`,
`run`, `approve` and `teardown` are additive — `scripts/samples.sh`,
`scripts/samples_harness.py`, `samples/fixtures/` and this page, plus the four
template files and the two `aistack` subcommands. Reverting the commit restores
the previous templates and leaves `samples load` behaving exactly as it did.
Run `samples teardown` first if the demo database is up; after a revert the
command that drops it is gone.

## 5. When something fails

**`'nomic-embed-text' is still not in 'ollama list' after a pull that reported
success.`** The pull helper ran but downloaded nothing. Run
`bin/aistack models pull nomic-embed-text` directly and read the output. Only
the short-lived pull helper can talk to the registry at all, so a failure here
is usually DNS or a proxy on the host rather than anything in the stack.

**`LiteLLM /v1/embeddings returned 401`.** The demo's virtual key was revoked
or `secrets/samples_demo_litellm_key` is stale. Delete that file and re-run
`samples setup`, which mints a new one.

**`n8n Task Broker's port 5679 is already in use.`** Something is running
`n8n execute` inside the container without the harness's alternate broker port.
Use `bin/aistack samples run …` rather than calling `n8n execute` by hand — it
passes `N8N_RUNNERS_BROKER_PORT=15679` precisely because the running main
already holds 5679.

**W4 leaves a container behind after a Ctrl-C.** `docker rm -f
aistack-samples-w4`, then `bin/aistack samples run W4` to finish putting the
demo away. The harness removes it on a clean interrupt; a `kill -9` of the
harness itself cannot.

**`syntax error at or near ":"`** from psql means a statement reached the server
with its `:'variable'` placeholders unexpanded. psql does not expand variables
in a `-c` string; the harness sends SQL on standard input for exactly this
reason.

**A case fails and you want the detail.** The evidence is in the demo database:

```sh
docker exec -i aistack-postgres psql -U aistack_demo -d aistack_demo \
  -c 'SELECT run_id, top_source, left(answer, 120) FROM w1_runs ORDER BY run_id DESC LIMIT 5'
docker exec -i aistack-postgres psql -U aistack_demo -d aistack_demo \
  -c 'SELECT action_id, state, outcome, created_at FROM approval_action ORDER BY created_at DESC LIMIT 10'
docker exec -i aistack-postgres psql -U aistack_demo -d aistack_demo \
  -c 'SELECT action_id, from_state, to_state, at FROM action_transitions ORDER BY seq DESC LIMIT 20'
```
